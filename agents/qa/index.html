Data notes

  • Synthetic logs from a seeded Python script, for a fictional brand: 13 weeks of nightly QA runs over the three other demo agents — every chatbot answer and every written brief, by day.
  • Source values are real for this site. Each flagged example is re-computed from the other agents' own demo data, as of the day it was asked — the share price from the CEO Morning Brief, sales and stock from the Product Performance Agent, email and journey figures from the eCom agent. The page shows the nightly re-check's recorded result for each claim, generated with the data; nothing is re-queried in your browser. Some examples are as of an earlier week than those pages let you pick; each one shows the date it was asked, and its source values are as of that date.
  • Claims = numbers, direction words ("up", "recovering"), rankings and periods in an output. The claim checker re-computes each one from the source, independently of what the agent read. The LLM judge scores accuracy, relevance and grounding from 1 to 5, after it sees the checker's result. A claim matches when its figure equals the source for the period and scope it names; the match rate is not an accuracy score for the agents, because whether the answer read the right scope, meant the right thing and drew a fair conclusion are separate checks.
  • An output is flagged when any claim doesn't match, or any judge score is 2 or lower. Flags are grouped by cause; a reviewer decides each one.
  • Inline check is the check each agent runs before it shows an answer: it compares the answer with what the agent read. The nightly run catches what it can't — inputs that were late, stale or the wrong slice.
  • Weeks run Monday to Sunday; this week is Nov 9–15. The other agents use their own fiscal calendars, so this page labels weeks by date.
  • Chatbot. Answers to the six suggested questions are built in the browser from the view you have selected, then checked before they show. A typed question that matches one gets the same answer; anything else gets "not in this data". This public page has no model, because it can't safely hold an API key.

What I built

Once the agents had chatbots, the riskiest thing on the page was no longer a chart — it was a sentence. A wrong number in a confident answer looks exactly like a right one. Each agent already checks its answers before showing them, but that check can only compare the answer with what the agent read: when the data it read is late, stale or the wrong slice, the answer passes — and is still wrong. Reading every conversation by hand doesn't scale.

I designed and built it: which claims it pulls out of an answer, how each one is re-computed independently of the agent, the judge's rubric, and the review loop that turns a confirmed mistake into a release test. It runs on the same framework as the agents it checks, and reads the same warehouse tables they do.

Now every output is checked every night, a flagged answer reaches its owner the morning after instead of when a user finds it, and agent owners only spend time on the few flags that need a decision. Every confirmed mistake becomes a release test, so the same check never has to be done by hand twice.

How it works

  1. Log everythingEvery chatbot answer and every brief is stored with what the agent read: which table, which filters, and when the data last loaded.
  2. Nightly runAt 2:00 every night the agent picks up the day's outputs from all the agents, so a problem is flagged by the next morning.
  3. Extract claimsEvery number, direction word, ranking and period becomes a claim: what it measures, for which scope and when.
  4. Re-compute from the sourceEach claim is re-computed with its own query, not from what the agent read. Match or mismatch — no opinions. This is what catches late or wrong inputs.
  5. Judge the restAn LLM judge scores accuracy, relevance and grounding against a fixed rubric, sees the checker's result, and explains its score.
  6. ReviewThe agent owner marks each flag a real issue or a false alarm. False alarms tune the judge; real issues get a fix and an owner.
  7. Release testEvery confirmed issue becomes a test that runs before every release, so a fixed mistake is re-tested before anything ships again. A Weekly QA report sums it up every Monday.
