Data notes

  • Synthetic data from a seeded Python script, for a fictional brand: 17 fiscal weeks of sessions and journey steps by channel and device, every email send, landing pages and 14 products.
  • Step % = share of the step before. Bounce = sessions that were not engaged (under 10 seconds, one page, no conversion), as in GA4. Cart abandonment = sessions with an add-to-cart that don't buy. Checkout completion = purchases ÷ sessions that started checkout.
  • Every comparison is with the prior period of the same length: last week, or the prior 4 weeks. Last year isn't in this agent.
  • Email. Open rate = opens ÷ delivered; click-to-open = clicks ÷ opens. Delivered, opens and clicks aren't split by device, so the email steps show for All devices only. Site results are matched to each send on its campaign tag.
  • Landing pages and products read all channels; they follow the Device and Period filters.
  • A release note, a stock-out, a campaign link and a review theme come from a small events file — the facts a real agent reads from other systems.
  • Summaries, alerts and Weekly Insights are written by rules over the same sums. In production an LLM writes the prose and a checker verifies every number.
  • Chatbot. Answers to the six suggested questions are built in the browser from the view you have selected, then checked before they show. A typed question that matches one gets the same answer; anything else gets "not in this data". This public page has no model, because it can't safely hold an API key.
  • Feedback review shows what the owner sees each week. The week is synthetic; your own 👍 / 👎 are added to it and stay in this browser.

The problem

The eCommerce team's Monday started with several separate reports — site traffic, the funnel, email results, product performance — each in its own tool. Answering "why did revenue drop?" meant lining them up by hand.

They needed one place that follows the shopper from the email to the order, finds the step that broke, and says why.

My role

I designed how the agent reads the journey: which steps it follows from the email to the order, how each rate is defined, the rules that find the biggest drop and explain it, and the guardrails on the chatbot.

It runs on the same framework as the Product Performance Agent — a new domain, without a new code base.

How it works

  1. Weekly refreshSite sessions, email sends and product data land in the warehouse: one row per week, channel and device.
  2. One journeyEmail delivered → opened → clicked joins the site journey on each send's campaign tag, so email and site read as one funnel.
  3. Find the breakRules compare every step with the prior period, find the biggest drop, and split it by device, channel and landing page.
  4. Explain itThe few facts other systems hold — a release, a stock-out, a campaign link — are matched to the break, so the summary says why, not just where.
  5. Weekly InsightsEvery Monday the agent writes the brief: what moved, why, and what to fix first, with an owner for each fix.
  6. ChatbotAnswers come only from this data, and every figure is cited to where it appears on the page. A checker confirms the numbers, direction words and rankings before an answer is shown.
  7. Feedback loopEvery answer can be rated, with a reason. Each week the agent groups the feedback and drafts fixes, the owner decides, and every fix becomes a regression test.

Outcome

One place for the eCom team's Monday. The site, email and product reports that used to live apart now sit in one view, so the weekly reporting starts from the same numbers — less time assembling, faster decisions.

The team uses it every Monday as part of its weekly reporting: the brief says what broke and who should fix it, and a follow-up question gets an answer in seconds.
